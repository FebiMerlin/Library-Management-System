# Регламент работы и правила оформления кода

## 1. Роли и коммуникация

| Роль | Отвечает за | Не делает |
|---|---|---|
| **PM** (Шарыгин) | ТЗ, план, трекер, общение с Заказчиком, ревью, приёмка | не коммитит код в `master` напрямую |
| **DevOps** (Хребитщев) | трекер, репозиторий, CI, IDE, сборочные скрипты, `infra/` | не меняет бизнес-логику без задачи |
| **Dev** (Хамидуллин) | код ядра и CLI, тесты, фичи, README, сценарий сдачи | не общается с Заказчиком напрямую |

* Все вопросы Заказчику — только через PM. Если PM выбыл, команда в тот же день назначает нового и сообщает Заказчику.
* Ежедневный короткий отчёт в трекере (комментарий к задаче или обновление процента). Синхронизация команды — 2 раза в неделю, 15 минут.
* Решения по архитектуре фиксируются в PR или в `docs/` — не в чате.

## 2. Работа с git

* Ветка `master` защищена: только через pull request, минимум 1 аппрув, зелёный CI.
* Именование веток: `feature/T31-return-books`, `fix/T25-input-validation`, `docs/T37-readme`, `infra/T13-ci`.
* Одна задача трекера — один PR. В описании PR: `Closes #<issue>` или ссылка на задачу.
* Коммиты — [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `refactor:`, `test:`, `build:`, `ci:`, `docs:`, `chore:`. Тема ≤ 72 символов, на английском; тело — по необходимости, объясняет *почему*.
* Перед PR: `cmake --build --preset debug` (тесты входят в сборку) и `clang-format` на изменённых файлах.
* Не коммитить: артефакты сборки, `*.dat`, IDE-файлы вне `.vscode/`, секреты (пароли, токены).
* Теги релизов: `v1.0.0` по SemVer; версия в `CMakeLists.txt` (`project(... VERSION)`).

## 3. Ревью кода

Проверяющий убеждается, что:
1. задача из трекера решена полностью, ничего лишнего не сделано;
2. есть тесты на новое поведение и на исправленный баг (тест должен падать без исправления);
3. нет предупреждений компилятора (CI с `-Werror`);
4. документация обновлена (README / FEATURES / TESTS), если поведение изменилось;
5. код соответствует разделу 4.

## 4. Правила оформления кода (C++)

Форматирование — автоматическое: `.clang-format` (база Google, отступ 4, строка 120). Проверяется в CI. Ниже — то, что clang-format не проверяет.

### 4.1. Структура
* Стандарт **C++17**, без расширений компилятора (`CMAKE_CXX_EXTENSIONS OFF`).
* `include/lms/` — публичные заголовки ядра; `src/core/` — реализация ядра; `src/cli/` — консольный интерфейс; `tests/` — тесты. Ядро **не** включает `<iostream>` и не знает о консоли.
* Один класс/группа функций — один `.h` + один `.cpp`. Заголовки с `#pragma once`.
* Порядок `#include`: заголовок модуля, стандартная библиотека, `lms/…`, локальные — clang-format расставляет сам.

### 4.2. Именование
| Сущность | Стиль | Пример |
|---|---|---|
| Пространства имён | `lowercase` | `lms`, `lms::cli` |
| Типы (классы, структуры, enum) | `PascalCase` | `Library`, `TxType` |
| Функции и методы | `camelCase` | `issueBook()`, `formatMoney()` |
| Переменные, параметры | `camelCase` | `initialDeposit` |
| Приватные поля | `camelCase_` с суффиксом | `books_`, `today_` |
| Константы, `constexpr` | `kPascalCase` | `kHeader` |
| Значения enum class | `PascalCase` | `TxType::BookIssued` |
| Макросы | `UPPER_CASE` с префиксом | `LMS_VERSION` |

### 4.3. Практики
* **Никаких** `using namespace std;` в заголовках и в глобальной области `.cpp`.
* Никаких глобальных изменяемых переменных. Состояние — в объектах.
* Сырые массивы и `char[]` не используются; `std::string`, `std::vector`, `std::array`.
* Владение памятью — только через RAII; `new`/`delete` в коде запрещены.
* Ошибки бизнес-логики возвращаются через `Result` (не исключения, не коды `-1`, не печать в консоль из ядра). Исключения — только для действительно исключительных ситуаций (нехватка памяти).
* Деньги — тип `Money` (целые центы). `double` для денег запрещён.
* Магические числа выносятся в `Config` или именованные константы.
* Каждая функция ядра проверяет входные данные и **не меняет состояние**, пока все проверки не пройдены.
* Комментарии объясняют *почему*, а не *что*. Комментарий, ссылающийся на исправленный баг из `ISSUES.md`, приветствуется.
* Предупреждения компилятора — ошибки (`LMS_WARNINGS_AS_ERRORS=ON` в CI). Подавлять предупреждения прагмами нельзя.

### 4.4. Тесты
* Фреймворк — GoogleTest; один файл `tests/test_<модуль>.cpp` на модуль ядра.
* Имя теста — `Модуль.ЧтоПроверяется` (`Loans.LateReturnIsFinedPerDay`).
* Тесты не зависят от порядка выполнения, не используют текущую дату (`Library::setToday`), не оставляют файлов.
* Исправление бага сопровождается тестом, который его воспроизводит.
* Сквозные тесты CLI — `tests/scripts/<имя>.in` + `.expect`.

## 5. Инструменты
| Инструмент | Версия | Назначение |
|---|---|---|
| CMake | ≥ 3.16 (presets — ≥ 3.21) | сборка |
| Компилятор | GCC ≥ 9 / Clang ≥ 10 / MSVC 2022 | C++17 |
| Ninja | любая | генератор по умолчанию в presets |
| GoogleTest | 1.15.2 (FetchContent) | тесты |
| clang-format | **23.1.1** (`pip install clang-format==23.1.1`) | форматирование; версия закреплена, чтобы результат совпадал с CI |
| VS Code + CMake Tools | актуальные | IDE (см. `.vscode/extensions.json`) |
