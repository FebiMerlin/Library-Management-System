## 2. Твоя роль по заданию — что ты «делал»

По ПДФ менеджер: подбирает трекер, ОС, сборочную инфраструктуру, IDE, правила оформления кода; согласовывает всё с DevOps и преподавателем; составляет ТЗ; заводит задачи; контролирует качество; сдаёт проект. Все эти документы существуют и подписаны твоей ролью — ты должен знать, что в них:

- **`docs/TZ.md`** — техническое задание. Цели, требования (FR-1…FR-10 к программе, BR-1…BR-7 к сборке и тестам, IR-1…IR-4 к инфраструктуре), этапы и сроки (14.09–05.10), порядок сдачи, ограничения. **Важно:** ТЗ ещё не согласовано с преподавателем — это ты и делаешь на защите (см. п. 4).
- **`docs/INFRASTRUCTURE.md`** — выбор с обоснованием. Главное запомнить:
  - *Трекер*: рассмотрели GitHub Projects, Vikunja, YouTrack, Jira, Taiga, Trello. Выбрали **GitHub Projects** — рядом с кодом, PR закрывают задачи, ноль администрирования, преподаватель видит без регистрации. Если кафедра требует размещения у себя — готова **Vikunja** (docker-compose в `infra/`, разворачивается за час, ресурсы 1 CPU / 1 ГБ).
  - *CI*: **GitHub Actions** — бесплатно, готовые образы четырёх ОС. Для кафедры — Gitea + act_runner с тем же файлом конфигурации.
  - *ОС сборочного хоста*: Ubuntu Server 24.04 LTS.
  - *IDE*: **VS Code** + CMake Tools + clang-format, конфигурация в репозитории; CLion и Visual Studio тоже работают.
  - Сводная таблица с ресурсами и сроками — §5, её можно показать преподавателю прямо с экрана.
- **`docs/PLAN.md`** — 40 задач с ролями, датами, оценкой в часах (≈72 ч), вехи M0–M5. Те же задачи заведены в трекере.
- **`docs/REGULATIONS.md`** — регламент: ветка `master` только через PR с ревью, Conventional Commits, правила именования в коде, тесты обязательны для каждого бага.

## 5. Вероятные вопросы и ответы

- **«Почему не Jira / Trello?»** — Jira требует регистрации организации и избыточна для трёх человек; Trello не умеет процент выполнения и не размещается у себя. GitHub Projects даёт всё требуемое и связан с кодом.
- **«Как тесты запускаются во время сборки?»** — В CMake есть цель `run_tests`, включённая в сборку по умолчанию и зависящая от программы и тестов; она запускает CTest. Упал тест — упала сборка. Отключается опцией `LMS_RUN_TESTS_ON_BUILD=OFF`.
- **«Почему форк чужого проекта?»** — Так требует задание: «группа на вход получает проект с GitHub». История автора сохранена, авторство указано в README.
- **«Что делал DevOps?»** — Форк и настройка репозитория, CI на четырёх платформах, трекер (40 задач, участники, канбан, поле процента), docker-compose для кафедры, конфигурация IDE. Всё в репозитории: `.github/workflows/ci.yml`, `infra/`, `.vscode/`, `CMakePresets.json`.
- **«Сколько заняло?»** — По плану ≈72 человеко-часа на три недели (14.09–05.10), см. `docs/PLAN.md`.
- **«Что не сделано?»** — Полноценная авторизация (вынесена за рамки ТЗ, вопрос к вам) и размещение на ресурсах кафедры (готово к развёртыванию, ждём ресурсы).
- **«Почему на Windows в CI Ninja, а не Visual Studio?»** — С генератором Visual Studio запуск тестов внутри сборки срабатывал раньше, чем появлялись собранные файлы; это выявили в CI (видно в истории PR #1) и перевели Windows на Ninja + MSVC. Это как раз пример работы CI.
