# Приложение к инструктажу PM: термины простыми словами и вопросы по ревизии

Читать после `PM.md`. Здесь — что означают слова, которые ты будешь произносить, и что отвечать, если по ним начнут копать.

## 1. Термины из шага «репозиторий и CI»

**Репозиторий (git, GitHub).** Папка с проектом, у которой запоминается вся история изменений: кто, когда и что поменял. Git — программа, которая эту историю ведёт; GitHub — сайт, где репозиторий лежит и виден всем. Наш: https://github.com/FebiMerlin/Library-Management-System.

**Форк.** Копия чужого репозитория в свой аккаунт с сохранением его истории. Задание требует взять чужой проект — мы сделали форк `abdulsamie10/Library-Management-System`. На странице репозитория это написано под названием: «forked from abdulsamie10/…». Первые три записи в истории — авторские (2023 год), дальше наши.

**Коммит.** Одно зафиксированное изменение с подписью и описанием. У нас их 17 сверх авторских, названия по стандарту Conventional Commits: `docs:`, `build:`, `test:`, `ci:` — по первому слову видно, что за изменение. Посмотреть: кнопка «Commits» на главной странице репозитория.

**Ветка и Pull Request (PR).** Работа ведётся не прямо в основной версии (ветка `master`), а в отдельной ветке; когда готово, создаётся PR — «запрос на слияние». В PR видно все изменения, их можно обсудить, и только после зелёной проверки его вливают в `master`. Наш основной PR — №1, в нём 13 коммитов и 5 прогонов проверки. Так требует регламент (`docs/REGULATIONS.md`): в `master` только через PR.

**CI (Continuous Integration, «непрерывная интеграция»).** Автоматическая проверка: каждый раз, когда в репозиторий попадает изменение, сервер GitHub сам скачивает проект, собирает его и запускает все тесты. Результат — зелёная галочка или красный крестик рядом с коммитом. Это и есть «сборочная инфраструктура» из задания. Наш CI — GitHub Actions; описан одним файлом `.github/workflows/ci.yml`.

**«Зелёные прогоны на 4 ОС».** ОС — операционная система. Наш CI собирает проект на четырёх: Ubuntu (Linux) с компилятором GCC, Ubuntu с компилятором Clang, Windows с компилятором MSVC (от Microsoft) и macOS. Плюс пятая проверка — форматирование кода (clang-format). Зачем четыре: у преподавателя или проверяющего может быть любая система, а разные компиляторы ловят разные ошибки — и это подтвердилось (см. п. 3). Вкладка Actions → любой прогон → пять зелёных строк.

**Компилятор.** Программа, которая превращает исходный текст на C++ в исполняемый файл. GCC, Clang, MSVC — три разных компилятора, все три наш проект собирают без единого предупреждения (в CI предупреждения считаются ошибками — это строгий режим, специально включён).

**CMake.** Описание того, как собирать проект: какие файлы, какие настройки, какие тесты. Один файл `CMakeLists.txt` вместо ручных команд. В исходном проекте его не было вообще — собрать можно было, только зная нужную команду наизусть. Задание требует «добавить описание проекта при помощи cmake» — сделано.

**Тесты и «проверка тестами во время сборки».** Тест — маленькая программа, которая проверяет один факт: «если внести $100, баланс станет $50 после комиссий», «если вернуть книгу на 3 дня позже — штраф $3». У нас 65 таких проверок. «Во время сборки» означает: они запускаются автоматически в конце команды сборки, и если хоть одна не прошла — сборка считается неудачной. Нельзя получить программу с известной ошибкой.

**Трекер, канбан, GitHub Projects.** Трекер — список задач с исполнителями, сроками и статусами. Канбан — доска с колонками по стадиям (у нас Backlog / Todo / In Progress / Review / Done), карточки перетаскиваются слева направо. GitHub Projects — встроенный в GitHub трекер, наша доска https://github.com/users/FebiMerlin/projects/3. Поле Progress — процент выполнения (требование задания).

**IDE.** Программа-редактор для разработчика (VS Code, CLion, Visual Studio). Мы выбрали VS Code и положили его настройки в репозиторий (`.vscode/`) — любой участник открывает папку и получает одинаковую среду.

**Docker / docker-compose (папка `infra/`).** Способ запустить сервисы (трекер Vikunja, git-сервер Gitea, сборочный агент) одной командой на любом сервере — это наш вариант «размещения на ресурсах кафедры», если преподаватель его потребует. Пока не развёрнут — нет сервера; готов к запуску.

## 2. Три проблемы из журнала ревизии — что говорить

Журнал `docs/ISSUES.md` — таблица: номер, серьёзность, где в исходном коде, что не так, как воспроизвели, как исправили и каким тестом закрыли. Всего 35 проблем. На защите назвать три ниже; если попросят ещё — открыть таблицу и читать любую строку, там всё есть.

### 1.1 — Добавление книг не работало вообще

*Что было.* В исходной программе при старте создавалось 15 книг-заглушек с названием «Title» и автором «Author», и счётчик книг сразу ставился в максимум (15 из 15). Поэтому пункт меню «Добавить книгу» всегда отвечал «Book limit reached» — лимит достигнут. Ключевая функция администратора не работала ни разу.

*Как нашли.* Собрали исходник, вошли администратором, нажали «добавить книгу» — сразу отказ.

*Как исправили.* Лимит теперь проверяется по реальному числу книг (и поднят до 100), заглушки заменены на 15 настоящих книг по программированию. Тест `Books.LimitAppliesOnlyWhenFull` проверяет, что отказ приходит только когда книги действительно кончились.

### 1.2 — Чтение за границей массива при выборе книги

*Что было.* Студенту показывали список книг с номерами 1–15 и просили ввести номер. Введённое число никак не проверялось и использовалось как индекс в массиве: ввёл 999 — программа читает память, где массива нет. Это «неопределённое поведение»: может отказать, может выдать книгу, может упасть — как повезёт. Это критическая ошибка безопасности.

*Как нашли.* Чтение кода (строки 202–210 исходника) и проверка: ввели 999 — программа обратилась к несуществующему элементу.

*Как исправили.* Книга теперь выбирается по ISBN (её уникальному номеру), и программа ищет её в списке; нет такой — вежливый отказ «Book not found». Никаких индексов «по номеру строки». Тест `Loans.IssueRejectsUnknownStudentOrBook` подсовывает несуществующие номера, 0 и −1 и проверяет отказ.

### 2.1 — Данные терялись при выходе

*Что было.* Всё — студенты, их балансы, книги — хранилось только в памяти программы. Закрыл окно — всё исчезло. При следующем запуске снова 15 заглушек и ни одного студента. При этом README проекта называл его «системой управления библиотекой».

*Как нашли.* Достаточно прочитать код: в нём нет ни одной операции записи в файл.

*Как исправили.* Это стала фича F1: состояние сохраняется в текстовый файл `library.dat` после каждой операции и загружается при старте. Запись безопасная — сначала во временный файл, потом замена, чтобы сбой не испортил данные. Битый файл не ломает программу — выводится сообщение с номером строки. Тесты: 9 штук на хранение (`Storage.*`) плюс сквозной `cli.script.persistence`, который запускает программу дважды и проверяет, что студент «пережил» перезапуск.

## 3. Вопросы, которые могут задать по ревизии, и ответы

- **«Как вы искали проблемы?»** — Три способа: чтение кода; сборка компилятором со всеми предупреждениями (их, кстати, не было — компилятор такие ошибки не видит, поэтому ревизия и нужна); запуск собранной программы с провокационным вводом (буквы вместо чисел, отрицательные суммы, несуществующие номера). Метод описан в шапке `docs/ISSUES.md`.
- **«Как оценивали серьёзность?»** — Четыре уровня: критическая — неправильная работа, порча памяти или потеря данных; высокая — функция не работает или дыра в безопасности; средняя — неверное поведение в частных случаях; низкая — качество кода и сопровождаемость. Итог: 3 / 9 / 14 / 9.
- **«Все ли исправлены?»** — Все, кроме двух, и это осознанно: 1.6 (полноценная авторизация с хешированием паролей — вынесли за рамки ТЗ, пароль теперь хотя бы не в коде, а в переменной окружения; это один из двух вопросов, которые я вам задаю) и 4.5 (у исходного репозитория нет лицензии — организационный вопрос, авторство указано).
- **«Почему не написали с нуля, раз так плохо?»** — Задание требует именно ревизию чужого проекта; это имитация работы с унаследованным кодом заказчика. Мы сохранили все функции оригинала (это требование FR-1 в ТЗ) и его историю в git.
- **«Как доказать, что баг был?»** — Исходный `main.cpp` лежит в `docs/original/`, в `docs/ACCEPTANCE.md` шаг 1 есть команды: собрать его и ввести те же данные — увидеть отказ «Book limit reached». Шарыгин может показать на месте.
- **«Как доказать, что баг исправлен?»** — На каждый исправленный баг есть тест, который его воспроизводит; имя теста указано в колонке «Статус» журнала. Если убрать исправление — тест упадёт, сборка станет красной.
- **«Что такое "неопределённое поведение"?»** (если спросят по 1.2) — Ситуация, для которой язык C++ не определяет результат: программа может сделать что угодно. Обращение за границу массива — классический пример; в реальных системах через такие ошибки взламывают программы.
- **«Почему деньги в центах?»** (проблема 1.12) — Исходник хранил суммы как дробные числа; в двоичном виде 0.1 + 0.2 ≠ 0.3, при многих операциях копейки «уплывают». Храним целое число центов — точно. Есть тест, который складывает 0.10 десять раз и требует ровно 1.00.
- **«Что с паролем?»** (проблема 1.6) — Был один пароль `"password"` на всех, прямо в тексте программы, и он же «защищал» студентов. Теперь пароль администратора задаётся снаружи (переменная окружения), студент входит по номеру зачётки. Полноценные учётные записи — за рамками ТЗ, готовы добавить, если вы решите.

## 4. Если спросят про CI подробнее

- **«Что происходит при каждом коммите?»** — GitHub запускает пять параллельных заданий: на Ubuntu с GCC, Ubuntu с Clang, Windows с MSVC, macOS — каждое скачивает проект, собирает его в строгом режиме (предупреждения = ошибки), запускает 65 тестов; пятое проверяет форматирование кода. Всё за 2–3 минуты. Результат виден во вкладке Actions и галочкой у коммита.
- **«CI когда-нибудь ловил ошибки?»** — Да, три раза в PR №1, и это видно в истории прогонов: (1) компилятор GCC на Linux нашёл потенциальное переполнение буфера при форматировании даты — на Windows-компиляторе этого не было; (2) на Windows оказалась новее версия Visual Studio, чем ожидалось; (3) при сборке через Visual Studio тесты запускались раньше, чем появлялись собранные файлы. Все три исправлены отдельными коммитами. Это и есть смысл CI — ловить то, что на одной машине не видно.
- **«Почему GitHub Actions, а не свой сервер?»** — Бесплатно, готовые машины четырёх ОС, нулевое администрирование, результат виден вам без регистрации. Если требуется размещение на кафедре — тот же файл `ci.yml` запускается на Gitea с агентом act_runner, всё в `infra/`, нужен хост 2 CPU / 4 ГБ / 20 ГБ.
